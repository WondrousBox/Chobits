# RSS 系统设计与实施计划

更新时间：2026-04-19

本文档用于沉淀当前项目中 RSS 功能的 review 结论、目标形态、产品呈现方案与分阶段实施计划。它不是一份脱离现有代码的理想化重构稿，而是基于当前仓库实现现状给出的可执行方案，目标是在尽量不打断现有功能迭代的前提下，把 RSS 从“部分可用”推进到“功能闭环、状态清晰、结构可维护”。

当前 review 依据主要来自以下实现入口：

- `electron/main/handlers/rss/ipc-main.ts`
- `electron/main/handlers/rss/types.ts`
- `electron/main/handlers/rss/sources/youtube-handler.ts`
- `electron/main/handlers/downloader/ipc-main.ts`
- `electron/main/db/repositories.ts`
- `src/pages/ResourcePage/RssFeedPage.tsx`
- `src/pages/ResourcePage/components/EditRssSettingsDialog.tsx`
- `src/pages/ResourcePage/hooks/useResourceOperations.ts`

## 1. Review 结论

### 1.1 总体判断

当前 RSS 实现已经具备一定闭环意识，尤其在以下几个方向上已经开始形成产品逻辑：

- 已有“订阅资源”这一独立资源形态，而不是把 RSS 只当成一次性导入动作。
- 已有 feed 拉取、缓存、手动刷新、下载条目、自动下载、删除订阅等完整链路的雏形。
- 已开始处理 YouTube 这类特殊源，并把通用 RSS 与源特化逻辑做了初步隔离。
- 已逐步收紧下载终态、错误提示和删除语义，说明实现方向是对的。

但从工程角度看，当前代码形态还不是一个稳定的长期方案，核心问题不是“有没有功能”，而是“状态来源是否单一、职责是否清晰、边界是否稳定”。

### 1.2 当前实现的主要问题

#### 问题 1：`rss/ipc-main.ts` 职责过重

当前 `electron/main/handlers/rss/ipc-main.ts` 同时承担了：

- feed 请求与 XML 解析
- 资源创建与更新
- feed item 入库与缓存读取
- 自动检查与自动下载调度
- 手动下载入口
- 删除逻辑
- YouTube 历史拉取入口

这会带来三个直接问题：

- 功能继续增加时，文件会快速失控。
- 状态变更散落在多个 handler 分支里，难以保证语义一致。
- 单元测试和回归验证几乎无法细化到稳定边界。

#### 问题 2：RSS 的“真实状态”分散在主进程与渲染层

目前 RSS 条目的展示状态来自多处拼接：

- `rss_feed_items` 中已有字段
- 资源库子资源是否已生成
- 下载任务运行时状态
- 渲染层临时维护的错误文案

这会导致：

- 相同条目在不同刷新时刻看到的状态不一致。
- UI 必须理解下载器内部细节才能正确渲染。
- 很多错误只存在于内存态，重启后丢失。

#### 问题 3：`metadata` 承担了过多隐式协议

当前 RSS 订阅与条目有不少行为依赖 `metadata` 中的约定字段，例如：

- `sourceType`
- `autoDownload`
- `downloadQuality`
- `fetchInterval`
- 与下载器联动需要的派生信息

问题不是不能用 `metadata`，而是当前约定缺少明确 schema 和边界，容易导致：

- 前后端对字段语义理解不一致
- 兼容逻辑不断堆积
- 很难区分“持久化业务字段”和“临时渲染补丁”

#### 问题 4：RSS 与下载器的边界虽然存在，但还不够稳定

RSS 功能并不只是“订阅和展示 feed”，它的产品闭环是：

1. 发现新条目
2. 判断是否需要自动下载
3. 选择正确下载地址
4. 交给下载器执行
5. 把下载结果回写为 RSS 条目状态
6. 把资源库中的实体与 RSS 条目关联起来

也就是说，下载不是“额外功能”，而是 RSS 的下游闭环之一。当前这条链路已经开始打通，但还存在如下风险：

- 条目真实下载地址的选择逻辑仍可能受源类型影响
- audio-only 资源的扩展名、媒体类型和入库策略仍需继续收口
- 下载任务成功、文件成功、入库成功三者的语义边界仍需长期固化

#### 问题 5：通用 RSS 与 YouTube 源的抽象还只完成了一半

当前项目已经有 `youtube-handler.ts` 和 `rssSourceRegistry` 的方向，这是正确的。但现状仍然是：

- 通用 XML 解析与源特化增强仍耦合较深
- 源能力模型不完整，例如“历史回填”“分页令牌”“下载地址推导”“媒体类型推导”还没有完全抽象出来
- 后续如果接入播客、Bilibili、专栏等源，扩展成本仍会偏高

#### 问题 6：错误处理和可观测性还不够产品化

当前已经开始区分“下载失败 / 入库失败 / 已取消”，这是很好的改进，但整体上仍然存在：

- 错误原因缺乏统一分类码
- 部分错误只在 toast 或内存态出现
- 很难回答“为什么这个订阅没有自动下载”“为什么某个条目长期失败”
- 缺乏围绕 RSS 的统计视角，例如最近同步时间、同步耗时、失败次数、自动下载命中率

### 1.3 结论

这套 RSS 实现的推进方式我认可，说明工程目标是清楚的；但结构设计我只认可一半。当前最适合的策略不是推倒重来，而是以“先补正确性，再收状态模型，再拆架构”的方式继续推进。

## 2. 系统目标与非目标

### 2.1 目标

RSS 系统最终应当成为一个稳定的“订阅源资源系统”，至少覆盖以下能力：

- 管理订阅源，而不是只做一次性导入
- 周期性发现新增内容，并保留可回看的条目历史
- 支持手动下载与自动下载
- 正确处理文章、视频、音频等不同媒体类型
- 能把下载结果稳定映射到资源库实体
- 让用户明确知道每个条目当前处于什么状态、失败在哪里、能否重试
- 对不同源类型保持可扩展架构

### 2.2 非目标

本阶段不建议把 RSS 系统扩展成以下方向：

- 不做完整的播客播放器或视频播放器系统
- 不做复杂推荐流或算法排序系统
- 不做重型的全文阅读器能力
- 不在第一阶段追求支持所有网站的深度定制抓取

RSS 的核心定位应当是：订阅、同步、筛选、下载、追踪状态。

- RSS 下载终态已开始收紧
  - 文件下载完成但未成功入库时，不再直接视为完成
- RSS 下载失败 UI 已开始区分语义

## 3. RSS 应实现的完整功能清单

### 3.1 订阅生命周期

### 应实现

- 创建订阅
  - 支持通过 URL 创建
  - 支持识别源类型，例如通用 RSS、YouTube
  - 创建时拉取一次 feed 预览，确认标题、封面、描述和源信息
- 编辑订阅
  - 启用/禁用订阅
  - 自动下载开关
  - 下载质量或下载模式
  - 同步频率
  - 源特有设置
- 删除订阅
  - 取消订阅但保留已下载资源
  - 取消订阅并删除已下载资源
  - 对批量删除与单条删除保持一致语义
- 展示订阅健康度
  - 最近同步时间
  - 最近成功同步时间
  - 最近失败时间
  - 未处理条目数

### 优先级

- P0：创建、编辑、删除、启用/禁用
- P1：健康度展示与批量操作

### 3.2 Feed 拉取与同步

### 应实现

- 手动刷新当前订阅
- 后台定时检查订阅更新
- 初次创建后的首轮缓存落库
- 增量同步，避免每次全量重新覆盖状态
- 去重策略
  - 优先使用稳定 item id
  - 其次使用 guid/link/mediaUrl 等组合键兜底
- 历史回填
  - 对支持历史拉取的源提供“继续拉更多历史内容”
  - 对不支持历史回填的源明确告知能力边界
- 分页读取
  - UI 只按页读取缓存，不一次性加载全部

### 关键要求

- 同步是“发现条目 + 归一化字段 + 写入缓存”的过程，不应在这一层直接混入 UI 逻辑。
- “是否自动下载”应建立在同步结果之上，而不是在解析阶段直接拼执行逻辑。

### 3.3 条目管理

### 应实现

- RSS 条目列表展示
- 条目搜索
  - 按标题、描述、作者筛选
- 条目筛选
  - 全部
  - 未读/未处理
  - 已下载
  - 下载中
  - 下载失败
  - 已跳过
- 排序
  - 发布时间倒序为默认
  - 支持按更新时间排序
- 条目详情信息
  - 标题
  - 描述
  - 封面
  - 发布时间
  - 作者
  - 媒体类型
  - 时长
  - 大小
  - 外链地址
  - 实际下载地址摘要

### 数据要求

- 条目应保留标准化后的基础字段，不应每次展示时重新从 XML 文本推导。
- UI 不应依赖下载任务事件临时补齐所有关键状态。

### 当前代码进度

- `RssFeedPage.tsx` 中的条目搜索已经落地
- `RssFeedPage.tsx` 中的条目状态筛选已经落地：全部、未下载、下载中、已下载、下载失败、已取消
- `RssFeedPage.tsx` 中的媒体类型筛选已经落地：全部类型、视频、音频、文章、图片、其他
- `RssFeedPage.tsx` 中的条目卡片已经显示媒体类型标签，缺失或未知类型会归入“其他”
- `RssFeedPage.tsx` 中的条目排序已经落地：默认按发布时间倒序，支持发布时间/更新时间的升序与降序
- `RssFeedPage.tsx` 中的筛选无结果空态已经支持一键清空搜索、状态筛选和媒体类型筛选
- `RssFeedPage.tsx` 中已经提供单条忽略入口，当前实现通过 `rss_feed_items.deletedAt` 软删除隐藏缓存条目，不复用下载状态表达忽略语义
- 失败或已取消条目已经具备明确的“重试下载”入口
- 当前筛选结果下已经支持批量重试失败或已取消条目
- 批量忽略、恢复忽略、更多异常空态与更完整的批量操作已全部实现
- 批量忽略：当前筛选结果中未下载且未在下载中的条目可一键忽略
- 恢复忽略：通过"已忽略"筛选状态查看被忽略的条目，支持单条恢复和全部恢复
- 订阅停用空态：引导用户打开设置启用订阅
- 同步失败错误态：显示错误原因并提供重试按钮

### 3.4 下载闭环

### 应实现

- 手动下载单个条目
- 自动下载新增条目
- 支持不同媒体类型的下载策略
  - article：可直接打开原文，必要时支持后续扩展为网页抓取
  - audio：音频资源下载与入库
  - video：视频资源下载与入库
  - image：图片资源下载与入库
- 正确选择下载地址
  - 优先条目级 `mediaUrl`
  - 无 `mediaUrl` 时回退 `link`
  - 对源特化资源允许 handler 覆盖推导
- 下载结果回写
  - 下载任务 id
  - 下载状态
  - 关联资源 id
  - 最后错误原因
  - 最近下载时间

### 为什么下载属于 RSS 功能范围

因为 RSS 对用户来说不是“看见新条目就结束”，而是“看见后能稳定消费”。在当前项目里，这种消费方式主要就是把条目下载并沉淀为资源库实体。因此 RSS 和下载器之间必须存在明确桥接层，而不是让 UI 临时拼接调用。

### 3.5 状态与错误模型

### 订阅级状态

订阅至少应有以下状态：

- `enabled`
- `syncing`
- `healthy`
- `warning`
- `error`

并提供以下观察字段：

- `lastCheckedAt`
- `lastSucceededAt`
- `lastFailedAt`
- `lastErrorCode`
- `lastErrorMessage`

### 条目级状态

条目至少应拆成两个维度，而不是一个字段包打天下：

- 内容同步状态
  - `discovered`
  - `cached`
  - `hidden`
  - `archived`
- 下载处理状态
  - `idle`
  - `queued`
  - `downloading`
  - `completed`
  - `failed`
  - `cancelled`
  - `skipped`

### 错误模型

建议引入统一错误码，而不是只存自由文本，例如：

- `feed_network_error`
- `feed_parse_error`
- `feed_auth_error`
- `download_no_url`
- `download_failed`
- `library_import_failed`
- `source_unsupported`
- `source_rate_limited`

错误文案可以面向用户友好，但错误码必须稳定，便于：

- UI 显示
- 重试策略
- 统计
- 问题排查

### 3.6 源适配能力

### 通用 RSS/Atom 源

- 标准 feed 拉取
- 标准 XML 解析
- enclosure 识别
- 基础媒体类型推导

### YouTube 源

- feed 拉取
- 历史回填
- 媒体地址推导
- 下载模式差异处理
- 特有元数据增强

### 后续应预留的源能力接口

- `fetchFeed`
- `fetchHistory`
- `normalizeItem`
- `resolveDownloadTarget`
- `getItemStableId`
- `getSupportedCapabilities`

这样后续接入播客源、站点源或更多视频源时，才不需要继续把逻辑堆进 `ipc-main.ts`。

### 3.7 可观测性与运维能力

### 应实现

- 订阅最近同步时间和结果
- 同步失败次数
- 条目发现数
- 自动下载命中数
- 下载失败数
- 用户手动触发次数
- 关键日志按订阅 id / 条目 id 可追踪

### 后续可扩展

- RSS 健康看板
- 失败原因排行榜
- 源类型成功率
- 自动下载耗时统计

## 4. 建议的产品呈现方式

### 4.1 资源列表中的 RSS 呈现

RSS 应继续作为一种资源类型存在，但列表卡片需要更明确表达“它是一个活的订阅源”，而不是静态资源。

建议卡片展示：

- 订阅标题
- 源类型标签，例如 `RSS`、`YouTube`
- 启用状态
- 自动下载状态
- 最近同步时间
- 未处理条目数量
- 最近错误提示（若存在）

建议卡片快捷操作：

- 刷新
- 打开订阅详情
- 编辑设置
- 删除订阅

### 4.2 RSS 详情页结构

建议 RSS 详情页拆为四个稳定区域：

### 区域 1：头部摘要

- 标题
- 描述
- 封面
- 源类型
- feed 地址
- 最近同步状态
- 订阅操作按钮

### 区域 2：状态栏

- 最近同步时间
- 最近成功时间
- 最近失败时间
- 未处理数量
- 下载失败数量

### 区域 3：筛选与操作栏

- 搜索输入框
- 状态筛选
- 媒体类型筛选
- 排序切换
- 刷新按钮
- 加载历史按钮

### 区域 4：条目列表

每个条目卡片建议展示：

- 标题与封面
- 发布时间
- 作者
- 媒体类型标签
- 是否已下载
- 下载状态 badge
- 错误原因简述
- 操作按钮：下载、打开原始链接、打开本地资源、重试、忽略

### 4.3 状态展示规范

状态标签要尽量稳定，避免一个状态同时承担技术语义和用户语义。

建议区分为：

- 订阅状态标签
  - 正常
  - 同步中
  - 有警告
  - 同步失败
- 条目状态标签
  - 未处理
  - 排队中
  - 下载中
  - 已下载
  - 下载失败
  - 已取消
  - 已跳过
- 错误提示区
  - 面向用户的短句
  - 可展开查看技术原因

### 4.4 删除交互

当前删除弹窗区分“仅取消订阅”和“同时删除已下载内容”的方向是正确的，建议正式固化为标准交互。

删除弹窗建议明确说明：

- 删除订阅只会停止后续同步
- 已下载资源默认保留
- 勾选危险选项后才会删除已下载资源
- 此操作不可撤销

### 4.5 空态与异常态

需要产品化处理以下场景：

- 首次创建但还没有任何条目
- feed 拉取失败
- 历史回填不可用
- 条目存在但全部下载失败
- 订阅已禁用

每种状态应当告诉用户下一步能做什么，而不是只显示错误文本。

## 5. 建议的数据与状态模型

### 5.1 订阅资源元数据

RSS 订阅资源元数据建议至少明确以下字段，并在类型层收口：

- `sourceType`
- `enabled`
- `autoDownload`
- `downloadMode`
- `downloadQuality`
- `fetchInterval`
- `lastCheckedAt`
- `lastSucceededAt`
- `lastFailedAt`
- `lastErrorCode`
- `lastErrorMessage`
- `capabilities`

其中：

- `downloadMode` 用于表达 audio/video/prefer-source-default 等行为，而不只是质量档位。
- `capabilities` 用于表达该源是否支持历史回填、分页、媒体下载等。

### 5.2 条目表建议承载的信息

`rss_feed_items` 建议成为 RSS 条目状态的单一事实来源之一，至少应稳定承载：

- `resourceId`
- `itemId`
- `title`
- `description`
- `link`
- `mediaUrl`
- `thumbnail`
- `author`
- `publishedAt`
- `updatedAt`
- `mediaType`
- `mediaFormat`
- `durationMs`
- `sizeBytes`
- `syncStatus`
- `downloadStatus`
- `downloadTaskId`
- `libraryResourceId`
- `lastDownloadAt`
- `lastErrorCode`
- `lastErrorMessage`
- `rawSourcePayload` 或可选精简原始字段

如果短期内不想做大迁移，也至少应补齐以下最关键字段：

- `downloadStatus`
- `libraryResourceId`
- `lastErrorCode`
- `lastErrorMessage`
- `lastDownloadAt`

### 5.3 UI 临时态与持久态的边界

应明确以下原则：

- 下载中进度百分比可以是运行时临时态
- 最终成功/失败状态必须回写持久层
- 错误原因不能只留在 toast 或 React state 中
- “是否已下载”应来自持久层关联，而不是靠前端二次推断

## 6. 技术架构建议

### 6.1 推荐拆分模块

建议把当前 RSS 实现逐步拆成以下模块：

- `rss-feed-parser`
  - 负责 feed 拉取、解析、标准化
- `rss-sync-service`
  - 负责同步、增量去重、入库、调度自动下载
- `rss-download-bridge`
  - 负责从 RSS 条目推导下载目标并与下载器对接
- `rss-delete-service`
  - 负责订阅删除、关联条目清理、可选子资源删除
- `rss-source-adapters`
  - 负责通用 RSS、YouTube 等源能力差异
- `rss-errors`
  - 负责错误码、错误文案与重试策略
- `rss-ipc-adapter`
  - 只暴露 IPC 入口，不承载核心业务

### 6.2 推荐职责边界

### `rss-feed-parser`

只做：

- 请求 feed
- 解析 XML/源响应
- 归一化为标准 `RssFeed` / `RssFeedItem`

不做：

- 入库
- 下载
- UI 文案拼装

### `rss-sync-service`

只做：

- 调用源适配器获取 feed
- 去重
- 写入条目
- 更新订阅同步状态
- 触发自动下载判定

不做：

- 下载器内部实现
- 视图层状态维护

### `rss-download-bridge`

只做：

- 根据条目和订阅设置决定下载地址和下载模式
- 组装下载任务 metadata
- 接收下载器结果并回写 RSS 条目终态

### `rss-ipc-adapter`

只做：

- 参数校验
- 调用 service
- 返回统一响应结构

### 6.3 建议的文件拆分

可按如下方向逐步落地：

- `electron/main/handlers/rss/ipc-main.ts`
  - 只保留 IPC 注册
- `electron/main/handlers/rss/rss-feed-parser.ts`
- `electron/main/handlers/rss/rss-sync-service.ts`
- `electron/main/handlers/rss/rss-download-bridge.ts`
- `electron/main/handlers/rss/rss-delete-service.ts`
- `electron/main/handlers/rss/rss-errors.ts`
- `electron/main/handlers/rss/rss-types.ts`
- `electron/main/handlers/rss/sources/base-source.ts`
- `electron/main/handlers/rss/sources/rss-source.ts`
- `electron/main/handlers/rss/sources/youtube-source.ts`

渲染层也建议按功能拆分：

- `src/pages/ResourcePage/rss/RssFeedHeader.tsx`
- `src/pages/ResourcePage/rss/RssFeedToolbar.tsx`
- `src/pages/ResourcePage/rss/RssFeedItemCard.tsx`
- `src/pages/ResourcePage/rss/useRssFeedState.ts`
- `src/pages/ResourcePage/rss/useRssDownloadState.ts`

## 9. 推荐实施顺序

建议按以下顺序推进，而不是一口气重构：

1. 先补正确性和状态持久化
2. 再补状态模型和错误码
3. 再做主进程架构拆分
4. 最后做 UI 体验和监控

原因很简单：

- 当前最容易出用户感知问题的是状态错判和失败不可解释
- 在状态模型不稳定之前，先做大规模重构容易把问题隐藏得更深
- 等数据语义稳定后再拆层，风险更低

## 10. 最小验收清单

当 RSS 功能达到以下标准时，可以认为进入“可稳定继续扩展”的阶段：

- 可以稳定创建、编辑、删除订阅
- 可以稳定拉取 feed 并去重缓存
- 可以明确区分订阅同步状态与条目下载状态
- 可以对新增条目进行手动下载与自动下载
- 下载结果可以稳定映射到资源库实体
- 失败原因可以跨刷新、跨重启保留
- 删除订阅时语义清晰且不会误删默认保留资源
- 通用 RSS 与 YouTube 至少完成一层清晰的 source adapter 边界

## 11. 风险与开放问题

当前仍有几个需要在实施中持续确认的问题：

### 风险 1：音频资源与视频资源的入库策略可能不同

如果下载器默认仍偏向视频文件路径或扩展名策略，audio-only 源在某些情况下仍可能被错误识别。这个问题应继续沿“下载目标推导 + 入库兼容策略”双向收口。

### 风险 2：不同源的稳定 item id 规则并不统一

如果 item id 不稳定，去重、历史回填、已下载状态映射都会出问题。需要在 source adapter 层明确每类源的 stable id 规则。

### 风险 3：历史回填能力不适合放在通用流程里硬编码

部分源支持分页历史，部分源只支持最近内容，必须通过能力声明决定是否展示“加载更多历史”。

### 风险 4：`metadata` 历史数据兼容会持续存在

后续补 schema 时，要预留迁移与兼容逻辑，避免一次性清理导致旧订阅异常。

## 12. 最终建议

如果只给一个总建议，那就是：

先把 RSS 明确定义成“订阅源同步系统 + 下载桥接系统”，不要再把它理解成单纯的 feed 展示功能。这样很多当前看似分散的问题就能统一解释：

- 为什么要改下载逻辑
- 为什么要收紧状态语义
- 为什么要持久化失败原因
- 为什么要做 source adapter

因为这些都不是附属优化，而是 RSS 成为完整产品功能的必要部分。
